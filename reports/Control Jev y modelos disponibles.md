# Deja que Jev guíe el control y descubre modelos

La vía adecuada es que Claude, Codex u otro motor configurado invoque una herramienta MCP común de OpenBot, mientras el servidor observa la pantalla, pide a Jev una decisión tipada y ejecuta la acción únicamente después de aplicar sus propias políticas. Jev no es un agente de ordenador: no recibe imágenes, no escribe texto libre y no ejecuta herramientas; es una capa rápida de decisión sobre estado textual y opciones cerradas ([System One](https://docs.typesafe.ai/concepts/system-one), [API](https://docs.typesafe.ai/api), [function calling](https://docs.typesafe.ai/cookbooks/function_calling)). Para los modelos, Codex ya ofrece un catálogo autenticado mediante su `app-server` experimental `model/list`; en Claude Code no encontré una interfaz documentada que enumere los modelos permitidos por una sesión de suscripción. Anthropic sí ofrece `GET /v1/models` para credenciales de API, pero la documentación no dice que enumere lo que puede usar una sesión OAuth de Claude Code ([Codex protocol](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs), [Anthropic Models API](https://platform.claude.com/docs/en/api/models/list)). Por tanto, OpenBot puede descubrir modelos Codex dinámicamente y mejorar Claude con alias y, si el usuario configuró una clave API, con el catálogo de esa clave; no debe presentar un catálogo global como si garantizara acceso individual.

## Jev decide los pasos; OpenBot conserva el control

La documentación de TypeSafe describe una API de petición-respuesta que recibe estado en texto/JSON y preguntas tipadas `choice`, `score` o `noul`, y devuelve opciones, puntuaciones o probabilidades. Las preguntas de una solicitud se evalúan independientemente en paralelo, lo que permite empaquetar la selección de operación, destino observado y nivel de riesgo en un viaje de red. La receta oficial de function calling confirma la frontera importante: Jev selecciona una función y argumentos cerrados; el código de la aplicación ejecuta esa función. No hay en la documentación revisada una API de ejecución de herramientas, MCP, visión, flujo de eventos ni streaming de Jev ([API](https://docs.typesafe.ai/api), [primitivas](https://docs.typesafe.ai/primitives), [function calling](https://docs.typesafe.ai/cookbooks/function_calling), [Jev y agentes de código](https://docs.typesafe.ai/introduction/coding-agents)).

OpenBot ya tiene la división principal: `ComputerProvider` observa y actúa; `fast-loop.ts` convierte la observación en estado estructurado, consulta `DecisionService` y valida la salida; Claude y Codex reciben herramientas MCP de OpenBot. Sin embargo, el camino de producción no entrega actualmente el texto que necesita una operación `type`: `ComputerAgentImpl.runTask` no proporciona `textForType`, por lo que ese paso escala en vez de completar la escritura. Además, `computer_task` es una llamada síncrona de tarea completa, no un protocolo explícito para guiar o cancelar una tarea en marcha. Estos son hallazgos del código local (`packages/computer/src/fast-loop.ts`, `computer-agent.ts`; `packages/mcp/src/tool-definitions.ts` y `services/computer-service.ts`), no afirmaciones de TypeSafe.

La recomendación es mantener un ejecutor único e independiente del proveedor y dar a todos los motores el mismo conjunto de herramientas MCP. El motor conversacional aporta la intención y, cuando haga falta, el texto que debe introducirse; OpenBot reduce la observación a título, URL, controles accesibles y valores pertinentes, pide a Jev que elija entre operaciones permitidas y destinos de esa observación, y valida la respuesta antes de pasarla al SPI y al broker. Jev no debe inventar el texto de formularios ni recibir capturas: su API documentada es de entrada textual y respuestas tipadas. Para steering mientras la tarea está activa, una extensión posible es separar `computer_task` (crea y devuelve `taskId`), `computer_steer` (añade instrucción o texto asociado) y `computer_cancel`, con eventos de progreso correlacionados por tarea y paso. Esa forma de API es una recomendación de diseño, no una capacidad ya implementada ni exigida por TypeSafe.

La confianza de Jev sirve como señal, no como permiso. OpenBot debe conservar comprobaciones deterministas de destino, acciones destructivas o sensibles, límites de pasos y concurrencia, y aprobación humana donde corresponda. Una respuesta inválida, baja confianza, timeout, indisponibilidad o límite de cuota debe detener o escalar la tarea; no debe activar una heurística que actúe silenciosamente. TypeSafe publica errores 429/529 y recomienda reintentos con espera exponencial, pero la ruta interactiva debería fallar rápido y ofrecer recuperación explícita; su página de modelos dice que los límites pueden cambiar y no publica una garantía de latencia por solicitud ([confidence routing](https://docs.typesafe.ai/patterns/confidence-routing), [API](https://docs.typesafe.ai/api), [models](https://docs.typesafe.ai/models)). El presupuesto local actual de 400 ms para la decisión `computer` es una elección de OpenBot, no un SLA de Jev. El bucle completo también incluye observación, políticas y ejecución del proveedor.

## Codex puede enumerar su catálogo autenticado

En la versión de Codex CLI examinada por la investigación (`0.157.1`), `codex models` no existe, pero el `app-server` implementa la solicitud JSON-RPC `model/list`, con paginación y opción `includeHidden`. El protocolo de OpenAI y su SDK oficial de Python muestran la solicitud y los tipos, y las pruebas del servidor verifican el catálogo visible, la paginación y la inclusión opcional de modelos ocultos ([protocolo de Codex](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs), [SDK oficial](https://github.com/openai/codex/blob/main/sdk/python/src/openai_codex/client.py), [pruebas oficiales](https://github.com/openai/codex/blob/main/codex-rs/app-server/tests/suite/v2/model_list.rs)). La investigación ejecutó esa consulta en una sesión local ya autenticada y obtuvo siete entradas visibles; es una observación puntual de esa cuenta y versión, no una lista para codificar ni una promesa de disponibilidad futura.

OpenBot ya comparte una instancia de `codex app-server` y su cliente JSON-RPC, pero `CodexDriver.listModels()` devuelve dos opciones fijas. El punto de integración recomendado es añadir tipos validados para `model/list`, paginar con `nextCursor`, solicitar `includeHidden:false` y mapear los identificadores devueltos al contrato actual `ModelInfo`. El endpoint existente `/api/models` ya alimenta el selector de perfil, así que la lista descubierta debe servir tanto al selector como al enrutamiento. Como `app-server` sigue marcado experimental, la integración necesita tolerar que el método no esté disponible, fallos de autenticación o proveedor y cambios de protocolo; en esos casos debe mostrar una indisponibilidad explícita o un catálogo obsoleto identificado como tal, sin sustituirlo silenciosamente por una lista vacía o por modelos ficticios. No se deben leer archivos OAuth ni extraer tokens: la autenticación debe quedarse dentro del CLI/app-server. La API pública `GET /v1/models` de OpenAI no equivale al catálogo disponible para una sesión de ChatGPT autenticada en Codex ([issue del CLI](https://github.com/openai/codex/issues/47059), [referencia de modelos API](https://developers.openai.com/api/reference/cli/resources/models)).

## Claude requiere distinguir alias, API y acceso real

La referencia de Claude Code documenta `--model` con alias o identificador completo y el selector interactivo `/model`, pero no documenta un subcomando de enumeración de modelos para la sesión autenticada. Los alias —por ejemplo `sonnet`, `opus` y `haiku`— son convenientes para CLI porque el proveedor resuelve su destino, pero cambian con el tiempo y no forman un inventario de permisos de cuenta ([CLI](https://code.claude.com/docs/en/cli-usage), [configuración y alias](https://code.claude.com/docs/en/model-config)). La API de Anthropic sí devuelve un catálogo paginado de modelos para una clave API; no se debe inferir que acepte credenciales OAuth de Claude Code ni reutilizarlas fuera del CLI ([Models API](https://platform.claude.com/docs/en/api/models/list)).

La mejora viable depende del tipo de autenticación. Para login de CLI, conservar alias soportados y permitir un identificador configurado manualmente es más honesto que mostrar IDs globales como accesibles. Para modo de clave API, OpenBot puede consultar desde el servidor local `GET /v1/models` con la clave ya guardada en su vault, validar la respuesta y devolver al UI únicamente IDs y nombres; nunca debe devolver cabeceras, claves ni errores sin sanitizar. La opción documentada `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` consulta `/v1/models` de un gateway compatible, no enumera por sí misma el acceso de una suscripción, y Anthropic advierte que un gateway compartido podría revelar a usuarios todos los modelos accesibles por su clave ([variables de entorno](https://code.claude.com/docs/en/env-vars)). Las restricciones empresariales `availableModels`, el proveedor, el plan y el estado de uso pueden limitar el acceso incluso cuando un modelo aparece en un catálogo ([restricciones de selección](https://code.claude.com/docs/en/model-config#restrict-model-selection)).

Conviene que el selector comunique la procedencia de cada opción —alias de CLI, catálogo de la clave API o valor manual— y trate el catálogo como descubrimiento, no como prueba de que la próxima generación funcionará. Las cuotas agotadas son distintas de los permisos de modelo: un modelo seleccionado puede fallar por límite de uso. Tampoco conviene probar cada ID generando una respuesta, porque esas pruebas consumen cuota y no garantizan disponibilidad posterior.

## La siguiente implementación debe cerrar dos brechas

Para computer control, la prioridad técnica es completar el paso de escritura con contenido proporcionado por el motor iniciador, verificar que el destino siga siendo un control observado y hacer que el MCP común esté disponible en ambos adaptadores. Después, un protocolo de tarea con IDs, steering, cancelación y eventos puede hacer que cualquier motor dirija una tarea activa sin apropiarse del ejecutor. Las pruebas deben cubrir errores y permisos con fakes; la exacta lista de herramientas inyectada en cada adaptador y la aplicación efectiva del broker en toda la ruta deben comprobarse antes de afirmar que ambos motores reciben idénticas garantías.

Para modelos, Codex tiene una ruta concreta de descubrimiento que puede implementarse ahora con compatibilidad experimental explícita. Para Claude, la solución debe ser condicional a la autenticación, porque las fuentes oficiales revisadas no ofrecen un endpoint que enumere los modelos accesibles por OAuth de Claude Code. En ambos proveedores, distinguir «detectado», «seleccionable» y «generación disponible ahora» evitará que el selector prometa más de lo que realmente sabe.

## Conclusión

Jev puede hacer rápido el juicio repetitivo del bucle, pero la velocidad no cambia quién controla la máquina: OpenBot debe observar, validar, autorizar y ejecutar cada paso. La interfaz compartida de MCP permite que el modelo configurado interprete la petición y dirija la tarea, mientras Jev selecciona acciones limitadas y OpenBot conserva la política y la intervención humana.

El descubrimiento de modelos debe reflejar la superficie real de cada proveedor, no perseguir una falsa lista universal. Codex ofrece un catálogo autenticado experimental; Claude ofrece alias documentados y un catálogo de API para claves API, pero no un inventario documentado de la sesión de suscripción. Esa diferencia debe mantenerse visible tanto en el diseño como en la interfaz.
